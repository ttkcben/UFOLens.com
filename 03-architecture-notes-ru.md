## Почему ufolens.com устроена именно так

Заметки о трех решениях, которые легли в основу [ufolens.com](https://www.ufolens.com) (поисковой многоязычной версии архива [PURSUE UAP](https://www.war.gov/ufo)). Приветствуются комментарии и критика.

### 1. Конвейер намеренно реализован как конечный автомат с переходом только вперед —

Состояния: `discovered → downloaded → ocr_done → translated → published`. Документ перемещается только вперед и только тогда, когда есть работа. Опубликованный контент никогда не перерабатывается повторно, если только детектор изменений (delta detector) не зафиксирует фактическое изменение источника.

**Почему:** OCR и перевод являются самыми затратными операциями, а архив со временем растет. Конвейер, который «перезапускает всё на всякий случай», имеет неограниченные затраты. Отсутствие возможности обратного перехода исключает риск неконтролируемого роста счетов. Потолок затрат является свойством графа состояний, а не результатом бдительности оператора.

**Цена:** миграции схем и намеренная повторная обработка намеренно неудобны. Приемлемый компромисс.

### 2. OCR и перевод работают на локальной LLM, а не в облачном API

OCR: open-source движок, резервный вариант в виде Tesseract CLI. Перевод + NER: Gemma через Ollama, на ноутбуке Apple Silicon.

**Почему:** нулевые предельные затраты на документ; воспроизводимость (фиксированная модель + промпты); и этап получения данных (fetch) в любом случае должен выполняться с резидентного IP (источник находится за Akamai Bot Manager —, поэтому `curl` получает 403), так что ноутбук в любом случае задействован в процессе.

**Цена:** качество перевода ниже, чем у передовых (frontier) моделей. Для справочного корпуса, где оригинал на английском всегда доступен в один клик, это приемлемо. Мы не претендуем на то, что переводы являются авторитетными.

### 3. Обе части имеют ровно один общий интерфейс: опубликованный бандл (bundle)

Конвейер никогда не пишет напрямую в продакшн-базу данных. Он генерирует `{ SQL, asset manifest, cache-purge list }`. «Публикация» = применение этого бандла (перенос SQL в edge SQL DB, синхронизация ресурсов с объектным хранилищем, очистка именованных ключей кэша).

**Почему:** локальная и edge-сторона могут развиваться независимо; бандл можно проверить (review); и данные для развертывания всегда имеют одну и ту же структуру. Worker представляет собой небольшое приложение TypeScript/Hono — со строгим CSP (без `unsafe-inline`; встроенный JSON-LD зафиксирован по версии sha256), `Accept-Language` + согласование страны $\rightarrow$ языка, 30-дневный кэш страниц в KV, ежедневный cron для обслуживания —, и ему никогда не нужно знать, как были созданы данные.

**Цена:** изменение схемы D1 затрагивает два файла (`pipeline/lib/manifest_schema.sql`, `db/schema.sql`). Недорогая страховка.

### Неизменные принципы, заложенные в поведение

- Не аффилировано с правительством США; никаких официальных знаков отличия.
- Редакции (замазывания) в источнике сохраняются и никогда не восстанавливаются.
- Видео приписывается DVIDS / AARO.
- `Tdm-Reservation: 1` + `X-Robots-Tag: noai, noimageai` по всему сайту —: доступно для индексации поисковиками, запрещено для скрапинга ИИ.
